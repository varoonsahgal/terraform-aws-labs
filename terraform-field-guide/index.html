Ground schoolThe mental model
01
Start here

The one idea: desired state

You don't tell Terraform what to do. You tell it what should exist. Terraform works out the steps by comparing three things: your configuration (desired), its state file (what it remembers building), and the real cloud (actual).

That's why running terraform apply twice in a row is safe. The second time, desired already equals actual, so the plan is empty: No changes. Your infrastructure matches the configuration.

Analogy

A thermostat. You set 21 °C; you don't say "run the heater for 14 minutes." It measures the room, compares, and acts only on the difference. Turn it up a degree and it does a little more work, not the whole job again.

Describe the destination. Terraform plans the route, and re-plans it every time.

02
Motivation

Why infrastructure as code

Clicking through the console ("ClickOps") is fine for exploring. It breaks down the moment you need to do it twice, explain what you did, or undo it.

QuestionConsole clicksTerraform
What exactly did we build?Go look, screen by screenRead the .tf files
Build it again in another RegionRepeat every clickChange one variable, apply
Who changed the firewall, and why?CloudTrail archaeologyGit history and pull request review
Preview a change before it happensNot possibleterraform plan
Tear it all down cleanlyHunt for leftoversterraform destroy
Analogy

A recipe vs. cooking from memory. Both can make dinner. Only one can be shared, reviewed, scaled to forty guests, and made the same way next month.

If it isn't in code, it isn't repeatable, reviewable, or reliably removable.

Part AThe language (HCL)
03
Syntax Lab 1

Anatomy of a block

Almost everything in Terraform is a block: a keyword, zero or more labels, and a body of arguments in braces. Learn to read one and you can read them all.

BlockWhat it declares
terraform { }Settings: required providers, versions, backend
provider "aws" { }How to connect to a platform (Region, default tags)
resource "type" "name" { }Something Terraform creates and manages
data "type" "name" { }Something Terraform only reads
variable "name" { }An input
locals { }Named, computed values
output "name" { }A value to print or hand to others
module "name" { }A call to a reusable package of Terraform
Tidbit

File names don't matter to Terraform. It loads every .tf file in the directory as one configuration. main.tf, variables.tf, and outputs.tf are a convention for humans.

Type tells Terraform what it is; the local name is how you refer to it. Neither is the name AWS shows.

04
Plugins Lab 1

Providers

Terraform itself knows nothing about AWS. A provider is a plugin that translates resource blocks into API calls for one platform. terraform init downloads the providers you list and records their exact versions in .terraform.lock.hcl.

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"   # any 6.x, never 7.0
    }
  }
}
Analogy

Travel plug adapters. Your laptop (Terraform) has one plug. Each country (platform) needs its own adapter (provider). You pack the adapters you need before the trip: that's init.

Trap

Added a new provider and got "Inconsistent dependency lock file"? You need to run terraform init again. Commit .terraform.lock.hcl so your whole team gets the same provider versions; never commit the .terraform/ folder.

Providers are plugins with versions. Pin them, lock them, and re-run init when the list changes.

05
Build vs look up Lab 1

Resources vs data sources

Reference a data source with the data. prefix: data.aws_ami.amazon_linux.id. Reference a resource without it: aws_instance.app_server.id.

Shared-account rule

Use data sources for shared things you must not own, like the default VPC. If you wrote resource "aws_vpc" for it, Terraform would try to create (and later destroy) a VPC instead of finding the one everyone uses.

Own it? resource. Just need to know about it? data.

06
Ordering for free Lab 1

References & the dependency graph

Whenever one block mentions another (vpc_id = aws_vpc.main.id), Terraform draws an arrow between them. All the arrows together form a dependency graph. Terraform creates things in arrow order, destroys them in reverse, and does everything without an arrow between it in parallel.

The address pattern for references is always TYPE.NAME.ATTRIBUTE, with data. in front for data sources and var., local., or module. for the others.

Trap

Reaching for depends_on by habit. You only need it when a dependency is real but invisible in the code (for example, an IAM policy that must exist before an app starts). If you can express it as a reference, do that instead.

Reference, don't sequence. The graph handles order and parallelism.

07
Inputs, workings, results Lab 1 Lab 2

Variables, locals, outputs

A Terraform configuration behaves like a function. Variables are its parameters, locals are its working variables, and outputs are its return values.

variable "user_id" {
  type        = string
  description = "Your assigned ID, e.g. user07"

  validation {
    condition     = can(regex("^user[0-9]{2}$", var.user_id))
    error_message = "user_id must look like user07."
  }
}

Where values come from (later wins)

  1. default in the variable block
  2. TF_VAR_user_id environment variable
  3. terraform.tfvars (loaded automatically)
  4. Any *.auto.tfvars files, alphabetically
  5. -var and -var-file on the command line, in the order given
Trap

testing.tfvars is not loaded automatically, only terraform.tfvars and *.auto.tfvars are. Forget -var-file="testing.tfvars" and Terraform prompts you for every variable without a default.

Variables are the knobs, locals are the wiring, outputs are the gauges.

Expressions Lab 2

The expressions toolbox

HCL isn't a full programming language, but it has enough to compute names, build lists, and render files. These cover most real configurations:

You want to…UseExample
Build a stringInterpolation"${var.user_id}-web"

Pull one attribute from manySplataws_instance.web[*].public_ip
Transform a listfor[for ip in local.ips : "http://${ip}"]
Build a mapfor with =>{ for i in aws_instance.web : i.id => i.private_ip }
Fill a file with valuestemplatefile()templatefile("boot.sh.tftpl", { name = var.user_id })

Try it

Trap

In a .tftpl file, every ${…} belongs to Terraform, even inside comments. Write $${HOME} when you want a literal ${HOME} to reach bash. A bare $HOME without braces passes through untouched.

When an expression gets clever, test it in terraform console before you plan.

Part BThe lifecycle
09
The most important habit Lab 1

Reading a plan

The plan is Terraform asking for permission. Read it the way you'd read a contract: symbols first, then the summary line, then anything marked # forces replacement.

SymbolMeaningDowntime risk
+CreateNone
~Update in place: same object, new settingsUsually none
-DestroyIt's gone
-/+Replace: destroy, then createHigh: gap between the two, new ID and IP
+/-Replace: create, then destroy (create_before_destroy)Lower: overlap instead of a gap
<=Read a data source during applyNone
 
  # aws_instance.beacon[0] must be replaced
-/+ resource "aws_instance" "beacon" {
      ~ id         = "i-0a1b2c" -> (known after apply)
      ~ public_ip  = "54.188.12.34" -> (known after apply)
      ~ user_data  = "3f9c…" -> "a71e…" # forces replacement
    }

Plan: 1 to add, 0 to change, 1 to destroy.
Shared-account rule

Before typing yes, find every Name in the plan and check it contains your ID. A destroy count you didn't expect means stop and ask.

Read the summary line out loud. If the numbers surprise you, don't type yes.

10
Terraform's memory Lab 1

State

terraform.tfstate is a JSON file that maps every address in your code to a real object ID in the cloud. Without it, Terraform couldn't tell your aws_instance.web apart from the 40 other instances in the account.

CommandWhat it does
terraform state listEvery address Terraform is tracking
terraform state show ADDRAll recorded attributes of one object
moved { from = … to = … }Rename an address without rebuilding the object
import { to = … id = … }Adopt an existing object into state
removed { from = … }Stop managing an object without destroying it
Analogy

A coat-check ledger. Your ticket says "hook 14"; the ledger says hook 14 is the blue coat. Lose the ledger and the coats are still on the hooks, but nobody can say whose is whose.

Trap

Never edit terraform.tfstate by hand, and never copy someone else's. Use the moved, import, and removed blocks, which show up in the plan for review.

Code says what you want. State says what you own. Lose the state, lose ownership.

11
When reality wanders Lab 2

Drift

Drift is any change made outside Terraform: a console click, a CLI command, another tool. Every plan starts with a refresh that reads the real objects, so drift shows up as a proposed change back to what the code says.

  • terraform plan -refresh-only shows drift without proposing fixes.
  • terraform apply -refresh-only accepts reality into state, for when the manual change was deliberate and you'll update the code next.
Tidbit

Terraform only notices drift in arguments it manages. Stop an EC2 instance in the console and plan won't restart it: aws_instance doesn't manage power state. (That's what aws_ec2_instance_state is for.)

If you clicked it, Terraform will un-click it. Change the code instead.

12
The costly difference Lab 2

Update vs replace

Some settings can change on a live object (tags, instance type after a stop/start). Others are baked in at creation (an instance's AMI or subnet, a bucket's name). Changing a baked-in setting forces replacement: a brand-new object with a new ID.

The lifecycle meta-argument

SettingEffectUse it for
create_before_destroy = trueBuild the replacement first, then delete the old oneAvoiding gaps (watch for unique-name clashes)
prevent_destroy = trueAny plan that would destroy it failsDatabases, state buckets
ignore_changes = [tags]Don't fight changes made elsewhere to these argumentsTags set by other tools, ASG desired count
replace_triggered_by = [...]Replace when something else changesRestarting on config change
Trap

create_before_destroy plus a fixed name fails: the new object can't take the name while the old one still holds it. That's another reason for prefixes and random suffixes.

A ~ is a tweak. A -/+ is a rebuild. Know which one you're approving.

13
Many of a thing Lab 2 Lab 3

count vs for_each

Both make multiple copies of a resource. The difference is how each copy is addressed, and that decides what happens when the list changes.

countfor_each
InputA numberA map or set of strings
Inside the blockcount.indexeach.key, each.value
Addressaws_instance.web[0]aws_instance.web["alpha"]
Best forN identical copies, or 0/1 on-off switchesDistinct, named things
Tidbit

Adding count to an existing resource is safe: Terraform automatically moves the old object to [0]. Switching from count to for_each is not automatic; write moved blocks for each element.

If the things have names, use for_each. If they're interchangeable, count is fine.

Part CWorking with others
14
Our classroom reality Lab 2

Shared accounts & naming

In a shared account, a name collision is the most common way to break your own lab, and someone else's. AWS enforces uniqueness at very different scopes:

The pattern that works

locals {
  name_prefix = "${var.user_id}-lab2"          # everyone's names start with their ID
}

provider "aws" {
  region = "us-west-2"
  default_tags {                           # every resource gets these, automatically
    tags = { Owner = var.user_id, ManagedBy = "terraform" }
  }
}

resource "random_pet" "suffix" {}            # for globally unique names

resource "aws_s3_bucket" "logs" {
  bucket = "${local.name_prefix}-logs-${random_pet.suffix.id}"
}
Shared-account rules

Prefix every name with your ID. Run Terraform only from your own directory. Never copy another person's state. Read every plan. Destroy when you're done, then prove it with a query on your Owner tag.

Prefix for people, random suffix for the planet, Owner tag for cleanup.

15
Beyond one laptop Lab 3

Remote state & locking

In the labs, state lives in a local file, which is fine for one person. A team needs state in one shared place, and a lock so two people can't apply at the same time.

terraform {
  backend "s3" {
    bucket       = "acme-terraform-state"
    key          = "team/app/terraform.tfstate"
    region       = "us-west-2"
    use_lockfile = true
    encrypt      = true
  }
}

Bootstrapping the bucket Lab 3

The state bucket can't keep its own state before it exists. The usual answer is a tiny bootstrap configuration, with local state, that creates the bucket once. Every other configuration then stores its state there under its own key.

Backend blocks can't use variables, because they're read before variables exist. Leave the block empty and pass the details at init time. That's partial configuration, and it's how one codebase serves many state files.

backend "s3" {}                       # in main.tf

# backend.hcl
bucket       = "user07-tfstate-a1b2c3"
key          = "user07/park/terraform.tfstate"
region       = "us-west-2"
use_lockfile = true

$ terraform init -backend-config=backend.hcl
Analogy

A library book. Anyone can read the catalogue, but only one person can check out the book at a time. Everyone else waits until it's returned.

Trap

Turn on versioning for the state bucket. If state is ever corrupted or overwritten, an older version is your undo button.

One state, one place, one writer at a time.

16
Reuse Lab 3

Modules

A module is a folder of Terraform with inputs (variables) and outputs. Every configuration you've written is already a module: the root module. Calling another module lets you stamp out the same pattern many times.

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"   # from the public registry
  version = "~> 5.0"

  name = "${var.user_id}-vpc"
  cidr = "10.0.0.0/16"
}

One module, many instances Lab 3

module "rides" {
  source    = "./modules/ride"
  for_each  = var.rides                 # a map(object({...}))
  ride_name = each.key
  thrill    = each.value.thrill
}
# address: module.rides["coaster"].aws_sqs_queue.line

A good module has no provider block and doesn't know who's calling it. Everything comes in through variables and goes out through outputs. That's what makes it reusable, and testable with mocks (sheet 23).

Analogy

A LEGO set's instruction booklet. You don't redesign a wheel for every car; you follow the wheel page and choose the colour.

Trap

Wrapping a single resource in a module just to rename its arguments adds a layer and buys nothing. Make a module when it captures a decision: a whole pattern with sensible defaults.

Modules are functions for infrastructure: inputs in, outputs out, internals hidden.

17
Don't leak

Secrets & safety

  • Credentials never go in .tf or .tfvars. Use aws configure, SSO, environment variables, or an IAM role.
  • sensitive = true on a variable or output hides it from CLI output, but the value is still stored in plain text in state.
  • State is a secret. It can contain passwords and keys. Store it encrypted with restricted access, and never commit it.
  • Newer Terraform (1.10+) adds ephemeral values and write-only arguments that never reach state, for providers that support them.

A starter .gitignore

# Terraform
.terraform/
*.tfstate
*.tfstate.*
crash.log
*.tfvars          # if they hold anything private
!example.tfvars   # …but keep a template

# DO commit
# .terraform.lock.hcl

Hidden in the terminal is not the same as hidden. Protect the state file like a password.

Shapes of data Lab 3

Complex types & optional()

Once a configuration is driven by data ("these are our rides", "these are our fleets"), the variable's type becomes a contract. A precise type catches typos at plan time, documents the shape for the next person, and lets callers skip fields that have sensible defaults.

variable "rides" {
  type = map(object({
    thrill    = number
    color     = optional(string, "#e2702b")   # optional, with a default
    max_tries = optional(number, 3)
  }))
}
TypeShapeUse for
list(string)Ordered, duplicates allowedSubnet IDs, CIDRs
set(string)Unordered, uniquefor_each over plain names
map(number)Keys to one value typeA traffic dial: { blue = 90, green = 10 }
object({…})Named fields, each with its own typeThe settings for one thing
map(object({…}))Many named things with settingsRides, fleets, environments
Trap

for_each accepts a map or a set, not a list. Lists are ordered, and reordering would reshuffle your resources. Wrap a list with toset() if the items are unique strings.

Type the data precisely, default what you can, and let the plan reject the rest.

19
Repeating nested blocks Lab 5

Dynamic blocks

count and for_each repeat whole resources. Sometimes you need to repeat a nested block inside one resource: one target_group per fleet, one ingress per port. A dynamic block generates them from a collection.

Tidbit

Rename the iterator with iterator = tg when the block name is long or nested dynamics would clash.

Trap

Dynamic blocks hide structure. If the nested blocks are fixed (always exactly two ports), write them out. Reach for dynamic only when the count really comes from data.

Repeat resources with for_each; repeat nested blocks with dynamic. Use both sparingly.

20
Adopting ClickOps Lab 4

Import blocks

Real accounts are full of things someone built by hand. An import block adopts an existing object into state without recreating it, and appears in the plan for review like any other change.

import {
  to = aws_sqs_queue.relic
  id = "https://sqs.us-west-2.amazonaws.com/123456789012/user07-museum-relic"
}
  • The id format differs per type: an SQS queue uses its URL, a parameter its name, an instance its i-… ID.
  • Generated config is a first draft: every attribute at its current value. Keep what matters; delete defaults.
  • Sensitive values come out as null # sensitive. Fill them in yourself.
  • Delete the import block after apply. It has done its job.
Shared-account rule

Only import what's yours. Importing a neighbour's resource makes your destroy delete it.

Import adopts; it never rebuilds. Review it in the plan like any other change.

21
Safe refactoring Lab 3 Lab 4

moved & removed

Renaming a resource, wrapping it in a module, or switching to for_each all change its address. To Terraform, a new address is a new object, so it plans to destroy the old one and create a new one. Two blocks tell it what you actually meant.

moved {
  from = module.coaster
  to   = module.rides["coaster"]
}

removed {
  from = aws_ssm_parameter.relic
  lifecycle { destroy = false }
}
Tidbit

These replace the old terraform state mv and state rm commands, which changed state silently with no review. Keep moved blocks around until every environment has applied them.

Change addresses in code, never by hand. The plan should say "moved", not "destroy".

22
Locks and smoke alarms Lab 4 Lab 5

Guardrails: conditions & checks

lifecycle {
  precondition {
    condition     = !var.fragile || var.retention_hours >= 72
    error_message = "Fragile exhibits must keep messages for at least 72 hours."
  }
  postcondition {
    condition     = self.sqs_managed_sse_enabled
    error_message = "Exhibit queues must be encrypted at rest."
  }
}

check "site_answers" {
  data "http" "site" { url = "http://${aws_lb.this.dns_name}/" }
  assert {
    condition     = data.http.site.status_code == 200
    error_message = "The site is not answering."
  }
}
Analogy

Preconditions and postconditions are locked doors: nobody gets through when the rule fails. A check block is a smoke alarm: it sounds every time you walk past, but it doesn't stop you.

Block what must never happen. Warn about what might be drifting.

23
Confidence without a cloud bill Lab 4 Lab 5

terraform test & mocks

terraform test runs .tftest.hcl files: each run block plans (or applies) the configuration with chosen inputs and checks assert conditions. With a mock_provider, no API is called, so tests are fast, free, and safe in a shared account.

mock_provider "aws" {
  mock_resource "aws_lb" {                     # realistic values for format checks
    defaults = { arn = "arn:aws:elasticloadbalancing:…" }
  }
}

run "bad_dial_rejected" {
  command   = plan
  variables { traffic = { blue = 50, green = 30 } }
  expect_failures = [var.traffic]                # this SHOULD fail
}
In a test fileDoes
run "name" { … }One scenario; command = plan or the default apply
assert { condition, error_message }Must be true after the run
expect_failures = [...]Passes only if those variables/resources/checks fail
override_data / override_resourcePin one object's values ("pretend the Region is eu-west-1")
mock_resource "type"Default values for every resource of a type
Trap

Mocks invent random strings, but providers still validate formats. Errors like "must begin with 'lt-'" or "invalid ARN" mean you need mock_resource defaults. And a check block's data source is deferred during a plan of new resources, so use a mocked apply for those runs. It still creates nothing.

Test the rules you'd be embarrassed to break. Mocks make it free.

24
Shipping without downtime Lab 5

Blue/green & the traffic dial

Replacing servers in place means a gap. Blue/green runs the old (blue) and new (green) versions side by side and moves traffic between them with load-balancer weights. Rollback is the same one-line change in reverse.

StrategyHowDowntimeRollback
Replace in place-/+ on the instanceYesRebuild again
create_before_destroyNew first, then delete oldBrief or noneRebuild again
Rolling refreshASG instance_refreshNone (reduced capacity)Another rolling refresh
Blue/greenTwo fleets + weighted listenerNoneSeconds: move the weights back
Trap

If traffic leaks into a launch template or user data, a dial change replaces instances, and the whole point is lost. The plan for a dial change should show only the listener.

Deploy the new version where nobody sees it. Then move traffic, not servers.

26
A–Z

Glossary

address
The unique path to an object in a configuration, such as aws_instance.web[0] or module.vpc.aws_subnet.a.
apply
Executes a plan, making real changes, then updates state.
backend
Where state is stored: local file by default, or remote (S3, HCP Terraform, and others).
blue/green
Running old and new versions side by side and shifting traffic between them with load-balancer weights.
bootstrap
A small configuration, with local state, that creates the remote-state bucket the other configurations use.
canary
Sending a small share of traffic (say 10%) to a new version before committing to it.
check block
A check { } with assertions evaluated on every plan and apply. Failures are warnings, never errors.
count
Meta-argument that creates N copies, addressed by index.
data source
A read-only lookup of something that already exists. Prefixed data.
default_tags
AWS provider setting that adds the same tags to every taggable resource.
dependency graph
The order Terraform derives from references between blocks.
desired state
What your configuration says should exist.
destroy
Removes every object in the current state.
drift
Differences between real infrastructure and state caused by changes outside Terraform.
dynamic block
Generates repeated nested blocks inside one resource from a collection.
expect_failures
In a test run, the list of variables, resources or checks that must fail for the run to pass.
for_each
Meta-argument that creates one copy per map key or set element, addressed by key.
HCL
HashiCorp Configuration Language, the syntax of .tf files.
idempotent
Running it again produces no further change. A second apply with no edits is a no-op.
import
Brings an existing real object under Terraform management. Use an import block so it shows in the plan.
init
Prepares a directory: downloads providers and modules and configures the backend.
lifecycle
Meta-argument block that changes create/destroy behaviour (prevent_destroy and others).
local value
A named expression inside a module (local.name). Can't be set from outside.
lock file
.terraform.lock.hcl: exact provider versions and checksums. Commit it.
mock provider

module
